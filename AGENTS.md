# Working in the Community Library

Instructions for coding agents and maintainers. [CONTRIBUTING.md](CONTRIBUTING.md)
sets the rules for solutions, versions, AI disclosure and verification; read
it first. This file gives the layout, the commands, and the maintainer
procedures that build on those rules.

## Layout

| Path | Contents |
| --- | --- |
| `models/<model>/` | The model description (`model-description.md` and its PDF), `myst.yml`, `CHANGELOG.md` and the submission guide (`README.md`). |
| `solutions/<model>/<NNN>-<toolkit>-<method>/` | One solution each, with its `metadata.yml`. `<NNN>` is the next free number within the model. |
| `docs/` | The website. `index.html`, `site.css` and `site.js` are hand-written; `docs/models/` is generated by `tools/build_pages.py` and not committed. |
| `templates/plain_latex_wide/` | The PDF template, including the version box. |
| `schemas/solution-metadata.schema.json` | The `metadata.yml` fields, and the four AI categories' words and summaries. |
| `tools/` | `build_pages.py` (description pages) and `check_metadata.py` (versions, disclosure and the library table). |

The AI categories' words and summaries live in the schema, which the tools
read. `templates/plain_latex_wide/template.tex` repeats them, so change both
together, and the definitions in `CONTRIBUTING.md` too.

## Checks before pushing

```sh
python -m pip install -r tools/requirements.txt
python tools/build_pages.py
python tools/check_metadata.py
```

The publishing workflow, `.github/workflows/publish.yml`, runs these, then
checks that local links, in-page anchors and the contents rail resolve. To
preview the site, serve `docs/` after building the pages; links to
directories such as `models/buffer-stock/` need a server:

```sh
python -m http.server 8000 --directory docs
```

The HARK solution's tests run from its directory, in an environment with its
own requirements:

```sh
cd solutions/buffer-stock/001-hark-egm
python -m pip install -r requirements.txt
python -m pytest -q checks
```

Running its notebook from that directory rewrites `results/` and the run's
settings in `metadata.yml`. If only floating-point noise changed, restore
them with `git restore metadata.yml results`.

## Changing a model description

Edit `models/<model>/model-description.md`, then follow the release steps in
[CONTRIBUTING.md](CONTRIBUTING.md#versioning-model-descriptions): raise
`options.version`, set `date`, add a `CHANGELOG.md` entry headed
`## <version> — <YYYY-MM-DD>`, and rebuild the PDF from `models/<model>/`:

```sh
myst build --pdf
```

The build needs LaTeX. Look at page 1 afterwards: the version box sits at
the top right and the title must start clear of it.

## Releasing a version

After the pull request merges, tag the merge commit and publish the release
with the PDF from that commit. The command is for a draft (0.x); drop
`--prerelease` and "(draft)" for a released version:

```sh
merge=$(git rev-parse origin/main)
out=$(mktemp -d)
git show "$merge:models/<model>/model-description.pdf" > "$out/model-description.pdf"
gh release create "<model>/v<version>" --target "$merge" --prerelease \
  --title "<Model name>, model description <version> (draft)" \
  --notes-file notes.md "$out/model-description.pdf"
```

Write `notes.md` as `CONTRIBUTING.md` describes. The
[buffer-stock/v0.1 release](https://github.com/QuantEcon/community-library/releases/tag/buffer-stock/v0.1)
is an example. Solutions' `model_description` links point at the tag, so
check that they resolve once it exists.

## The library table

Each filled slot in `docs/index.html` is written by hand, and
`tools/check_metadata.py` checks it against the solution's `metadata.yml`.
To add one, copy the HARK slot and change:

- `href`, and `data-solution` to the solution's directory;
- `data-version` and the label, `<toolkit> · <method> · <submitter> · v<version>`,
  where the submitter is `project`, or else the first author's surname;
- the `ai-chip`'s `data-level` and word;
- the tooltip in `title`.

Once a person verifies the solution against its current version, set
`data-verified="true"` and remove the slot's hidden "not yet verified" text.
A verified description's button takes `data-verified="true"` the same way.

## Conventions

- Pull requests have been squash-merged, and the squash commit's message on
  `main` joins the pull request's commit messages. Write each commit message
  to stand on its own: a short headline in the imperative and a body that
  explains why.
- Write "closes #N" or "fixes #N" only to close that issue on merge. GitHub
  reads those words as a closing instruction in commit messages and pull
  request descriptions alike.
- Each solution is authored and maintained by its submitters. Change one only
  with its maintainers' approval.
